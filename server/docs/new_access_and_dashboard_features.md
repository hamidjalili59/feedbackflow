# ویژگی‌های جدید UI و نحوه استفاده

این سند برای نسخه جدید client/server نوشته شده و توضیح می‌دهد تغییرات تازه چه کاربردی دارند و کاربران چطور باید از آن‌ها استفاده کنند.

## 1. انتخاب تکی و چندانتخابی با UI جدید

فیلدهای `single_choice` و `multiple_choice` دوباره طراحی شده‌اند تا در موبایل، تبلت و دسکتاپ خواناتر و قابل لمس‌تر باشند.

### انتخاب تکی

کاربر برای سوال‌هایی که فقط یک پاسخ دارند، یکی از کارت‌های بزرگ را انتخاب می‌کند. کارت انتخاب‌شده با border آبی، سایه نرم و نشان تایید مشخص می‌شود.

کاربرد مناسب:

- انتخاب یک گزینه از چند سطح رضایت
- انتخاب یک کلاس، شعبه یا سرویس
- سوال‌های بله/خیر سفارشی که بیشتر از دو گزینه دارند

### چندانتخابی

کاربر می‌تواند چند کارت را انتخاب کند. بالای لیست، تعداد گزینه‌های انتخاب‌شده نمایش داده می‌شود.

کاربرد مناسب:

- انتخاب چند فعالیت مورد علاقه
- انتخاب چند دلیل نارضایتی
- انتخاب چند دانش‌آموز/کلاس/خدمت مرتبط با پاسخ

در دسکتاپ، اگر عرض کافی وجود داشته باشد و تعداد گزینه‌ها زیاد باشد، گزینه‌ها به‌صورت دو ستونه نمایش داده می‌شوند تا فرم بیش از حد بلند نشود.

## 2. ورود مهمان

ورود مهمان دیگر فقط به پیام «از لینک وارد شوید» محدود نیست. برای ورود مهمان دو حالت وجود دارد.

### حالت اول: ورود از لینک عمومی فرم

اگر کاربر از مسیر عمومی فرم وارد شود، مثل:

```text
/public/<public_token>
```

سازمان از همان `public_token` تشخیص داده می‌شود و مهمان می‌تواند session محدود بگیرد.

### حالت دوم: ورود مهمان با کد سازمان

اگر کاربر از صفحه login معمولی روی «ورود میهمان» بزند، یک bottom sheet باز می‌شود و از او می‌خواهد:

- کد یا slug سازمان را وارد کند
- نام نمایشی خودش را وارد کند

این تصمیم برای جلوگیری از session مهمان بدون سازمان است. مهمان باید حتماً به یک organization مشخص وصل شود تا دسترسی‌ها، فرم‌ها و داده‌ها قاطی نشوند.

پیشنهاد محصولی: در تنظیمات سازمان، یک `slug` ساده و قابل اعلام تعریف شود؛ مثلاً:

```text
main-school
campus-1
summer-camp-27
```

## 3. بررسی دسترسی قبل از پاسخ‌دهی فرم

قبلاً ممکن بود کاربر فرم را کامل پر کند و در انتها هنگام submit با خطای دسترسی روبه‌رو شود. اکنون صفحه پاسخ‌دهی قبل از نمایش سوال‌ها endpoint زیر را صدا می‌زند:

```text
GET /api/v1/forms/{id}/answer-access
```

اگر کاربر دسترسی پاسخ‌دهی نداشته باشد، همان ابتدا پیام واضح می‌بیند و سوال‌ها نمایش داده نمی‌شوند.

دلایل احتمالی عدم دسترسی:

- فرم برای کاربر assign نشده است
- فرم هنوز منتشر نشده است
- زمان پاسخ‌دهی هنوز شروع نشده است
- مهلت پاسخ‌دهی تمام شده است
- کاربر قبلاً پاسخ داده و پاسخ مجدد مجاز نیست
- فرم فقط با public link قابل پاسخ‌دهی است

اگر فرم public token داشته باشد، دکمه «باز کردن لینک عمومی» هم نمایش داده می‌شود.

## 4. عدم نمایش فرم‌های غیرقابل مشاهده

لیست فرم‌ها سمت سرور و client محافظت شده است. فرم‌هایی که کاربر اصلاً اجازه مشاهده آن‌ها را ندارد، تا حد ممکن در لیست فرم‌ها نمایش داده نمی‌شوند.

قانون کلی:

- مدیر، ادمین، CEO و Super Admin فرم‌های مدیریتی مجاز خود را می‌بینند.
- سازنده فرم فرم خودش را می‌بیند.
- کاربران عادی فقط فرم‌های منتشرشده، قابل مشاهده یا assign شده را می‌بینند.
- برای پاسخ‌دهی، علاوه بر مشاهده، `answer-access` هم بررسی می‌شود.

## 5. ساخت فرم و دکمه‌های ایجاد فرم

دکمه ساخت فرم فقط برای نقش‌هایی نمایش داده می‌شود که منطقی است فرم بسازند:

- teacher
- manager
- admin
- ceo
- super_admin

برای parent، student و guest دکمه ساخت فرم مخفی می‌شود تا کاربر وارد صفحه‌ای نشود که احتمالاً اجازه استفاده از آن را ندارد.

## 6. تخصیص فرم به افراد یا segmentها

مدیر و CEO می‌توانند فرم‌ها را برای مخاطبان خاص assign کنند؛ مثلاً:

- دانش‌آموزان شرکت‌کننده در اردوی ۲۷ام
- معلم‌های یک پایه
- والدهای یک کلاس
- چند کاربر مشخص
- یک گروه یا segment داینامیک

برای این کار باید از بخش assignment فرم استفاده شود. سمت سرور این مدل‌ها پشتیبانی می‌شوند:

- user
- role
- group / class / department
- organization
- segment

برای سناریوی «اردوی ۲۷ام»، ابتدا یک Audience Segment ساخته می‌شود و اعضای اردو یا قوانین آن segment مشخص می‌شوند، سپس فرم به همان segment assign می‌شود.

## 7. شاخص‌های داینامیک

شاخص‌هایی مثل «ورزش»، «آموزش»، «انرژی»، «انگیزه»، «ارتباط با مدرسه» و «رضایت» ثابت و hard-code نیستند. مدیر یا CEO می‌تواند آن‌ها را تعریف، تغییر یا حذف کند.

هر شاخص می‌تواند به این منابع وصل شود:

- پاسخ یک field مشخص
- امتیاز کل submission
- درصد امتیاز
- تعداد submissionها

کاربرد:

1. مدیر شاخصی مثل `sports_participation` با عنوان «ورزش» تعریف می‌کند.
2. برای آن mapping تعریف می‌کند که از کدام فرم و کدام field محاسبه شود.
3. داشبورد والد، معلم، مدیر یا CEO آن شاخص را در کارت‌های dashboard نمایش می‌دهد.

## 8. پیشنهادهای باقی‌مانده برای طراحی دقیق‌تر

برای رسیدن به بیشترین شباهت به طرح نهایی، هنوز این موارد از تیم طراحی یا محصول لازم است:

- فایل Figma نسخه موبایل و دسکتاپ
- SVG یا PNG جداگانه آیکن‌ها و illustrationها
- وضعیت‌های دقیق هر نقش در dashboard
- متن نهایی empty stateها، خطاها و پیام‌های دسترسی
- تعریف دقیق segmentهای پیش‌فرض سازمان
- تعریف شاخص‌های پیش‌فرض و mapping هر شاخص به فرم‌ها و fieldها
- تصمیم درباره اینکه ساخت و ویرایش Metric/Audience Segment در client فقط برای مدیر باشد یا برای CEO هم جداگانه سطح دسترسی داشته باشد
